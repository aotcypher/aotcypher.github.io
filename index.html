맡은 일

PM으로 일정과 WBS, 회의록, 팀원 보고서 통합, 발표와 시연 영상을 맡았고, OPNsense 담당으로 WireGuard 사설망, 서버별 최소 허용 방화벽, HTTPS 리버스 프록시, NAXSI 웹 방화벽, Suricata 침입 탐지, Graylog 연계, 설정 백업과 복원을 직접 구축하고 검증했습니다.

웹, 게임, DB, 로그, 백업 서버는 팀원이 각자 맡았고, 저는 그 사이의 통신과 보안 정책을 정하고 실제 출발지에서 종단 시험을 했습니다.

문제 해결

ZAP이 High 경고를 냈다. 정말 취약점일까

상황
인증 후 고강도 스캔에서 SQL Injection High 후보가 나왔습니다.
판단
첫 시험의 후보 16건은 실제 응답을 보니 요청 제한(429), 로그인 이동(302), 로그인 화면(200)이었습니다. 재시험의 후보 2건은 운영 배포본의 코드에서 Prepared Statement와 파라미터 바인딩을 확인했습니다.
결과
확인된 High 0건. 도구 경고는 응답, 로그, 코드로 대조한 뒤에 결론을 냈습니다.

웹 방화벽을 언제 차단 모드로 바꿀까

상황
바로 차단하면 정상 기능이 막힐 수 있고, 학습 모드로만 두면 막지 못합니다.
판단
학습 모드에서 정상 100건과 공격형 200건을 흘려 오탐과 탐지율을 먼저 쟀습니다. 탐지가 몰리는 로그 검색과 이슈 생성 두 경로만 학습 모드로 남겼습니다.
결과
나머지 전체를 BLOCK으로 전환하고 차단 3/3, 정상 회귀 8/8을 확인했습니다.

Suricata가 일반 공격 200건을 하나도 잡지 못했다

상황
ZAP의 일반 공격형 요청 200건에서 Suricata 경고가 0건이었습니다.
판단
장애가 아니라 시그니처 범위의 차이였습니다. 웹 공격은 NAXSI와 웹 애플리케이션 통제가 맡고, Suricata는 활성 규칙 8/8 일치로 탐지 경로를 검증했습니다.
결과
미탐 결과를 숨기지 않고 한계로 보고서에 적었습니다. 승인 없이 IPS 차단 모드로 바꾸지 않았습니다.

백업 파일이 있다고 복원되는 것은 아니다

상황
백업 서버가 각 서버에 접속해야 하므로 백업 경로가 새로운 공격 경로가 될 수 있었습니다.
판단
백업 서버가 제한 계정으로 가져오는 Pull 방식으로 정하고 역방향 규칙은 만들지 않았습니다. OPNsense에는 백업 전용 계정과 API 키를 두고 출발지를 백업 서버 한 대로 묶었습니다.
결과
암호화된 설정을 격리 VM에서 복호화해 해시를 대조하고 실제로 복원해 14분 23초를 측정했습니다.

로그 저장소가 인증 없이 열려 있었다

상황
백업 상태 확인을 위해 열어야 할 OpenSearch 9200 포트가 평문 HTTP, 무인증 상태였습니다.
판단
로그 서버에서 백업 서버로 가던 SSH 규칙을 지우고, 백업 서버에서 9200으로 가는 규칙 하나로 바꿨습니다. TLS와 계정 분리 계획을 함께 검토했고 로그 담당자가 적용했습니다.
결과
무인증 접근 401, 역할별 계정 분리, 자동 스냅샷 성공을 확인했습니다.

각자 완료라는데 연결하면 안 된다

상황
담당자별 완료 보고는 설정 기준이었고, 실제 출발지에서 기능과 로그 저장까지 확인한 것은 아니었습니다.
판단
완료를 연결, 기능, 로그 저장, 복원의 단계로 나누고 실제 출발지에서 다시 시험했습니다. 여러 기록이 충돌하면 최근의 실제 시험 결과를 기준으로 통합 기준본을 하나 만들었습니다.
결과
보고서의 표 한 칸까지 설정, 시험 결과, 증빙과 연결했습니다.
PM으로 한 일
  • WBS와 회의록을 실제 적용 결과와 대조해 관리하고, 담당자별 잔여 작업을 실행 지시문으로 나눴습니다.
  • 팀원 인프라 보고서 6종을 하나의 인프라 구축 보고서로 통합하고, 수행 결과 보고서의 네트워크와 보안 파트를 썼습니다.
  • OPNsense를 처음부터 다시 만들 수 있도록 설치부터 백업, 복원까지 담은 인수인계서를 썼습니다.
  • 25분 발표를 문제, 설계, 구축, 검증, 성과 순서로 구성하고, 시연 영상을 6차까지 편집했습니다.
